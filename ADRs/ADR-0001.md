# ADR-0001: Engineering Conventions (Language, PR Target, Commits)

- **Status:** Accepted
- **Date:** 2026-03-19
- **Deciders:** Forever Snaps team
- **Technical Story:** FSP process standardization

## Context

The project needs clear collaboration standards so development stays consistent across contributors.  
Without explicit conventions, we risk mixed-language code, incorrect PR base branches, and inconsistent commit history.

## Decision

### 1) English-only engineering language

All software artifacts must be written in English, including:

- Source code (identifiers, function names, class names, variables)
- Comments
- Commit messages
- Pull request titles and descriptions
- Technical documentation (README, ADRs, issues, board cards)

### 2) Pull Requests must target `develop`

Every pull request must use `develop` as the base branch.

- Feature branches are created from `develop`
- PRs are opened **into** `develop`
- Direct PRs to `main` are not allowed (except explicitly approved release/hotfix workflows)

### 3) Commit message format

All commits must follow this structure:

`fix|feat|chore|refactor: [FSP-<ticket>] [<Name>] <message>`

#### Allowed types

- `fix`
- `feat`
- `chore`
- `refactor`

#### Example

`feat: [FSP-123] [Fabian] Allowing to upload photos to S3`

## Consequences

### Positive

- Consistent and searchable git history
- Cleaner release management through `develop`
- Better readability and onboarding for all contributors

### Trade-offs

- Contributors must follow stricter formatting rules
- PR validation checks may be needed to enforce standards

## Enforcement (recommended)

- PR template reminding base branch = `develop`
- Branch protection rules on `main`
- Commit linting or CI regex validation for commit format

### 4) Branch naming must be ticket-based

Branch names must start with the ticket identifier.

Format:

`FSP-<ticket-number>`

Examples:

- `FSP-123`
- `FSP-456`
- `FSP-789`
